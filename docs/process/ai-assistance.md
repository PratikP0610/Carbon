# AI Assistance Disclosure

Carbon was built with substantial AI assistance from Google Antigravity (powered by Gemini). This document is a transparent record of that involvement, in the spirit of responsible AI development practice.

---

## What Was AI-Assisted

### Code Generation

The majority of Carbon's Python backend and Swift macOS client code was **generated by Google Antigravity under the direction of the project owner**. This includes:

- `src/carbon/` — FastAPI server, orchestrator, CMS, intelligence engine, memory engine, governance engine, tools, metrics, providers
- `apps/macos/Carbon/Sources/` — SwiftUI client, WebSocket transport, process supervisor, memory monitor, single-instance lock
- `tests/` — Unit, integration, performance, and security test suites
- `docs/` — Architecture documentation, security analysis, benchmark reports
- `.github/workflows/ci.yml` — CI/CD pipeline
- `Makefile`, `pyproject.toml`, `requirements.lock`

### Documentation

All documentation files in `docs/` were drafted or substantially revised by AI, including architecture diagrams, API references, security threat models, and verification reports. The project owner reviewed and approved each document.

## What Was the Project Owner's Work

The following represent the **project owner's (Pratik Pradeshi's) independent contributions**:

### Architectural Decisions

- **Local-first design:** The choice to run everything on `127.0.0.1` with no cloud dependency.
- **Single-model concurrency:** The CMS exclusive-lease architecture that serializes inference.
- **Governance ladder:** The P0–P4 permission and A0–A3 autonomy framework design.
- **Research questions:** The five research questions and the EXP-000 experiment design.
- **SQLite over vector database:** The decision to use embedded SQLite (WAL + FTS5) rather than a vector database for memory.
- **Apple Silicon focus:** The choice of M5 MacBook Air as the development and target platform.

### Project Requirements

- The Product Requirements Document (PRD) defining Carbon's 10 design principles, feature scope, and non-negotiables.
- Acceptance criteria for each development stage (Stages 1–7).
- Formal stage acceptance decisions based on test evidence review.

### Validation and Review

- Review and acceptance of all test results.
- Identification of discrepancies between documentation and implementation.
- Direction to investigate and correct inaccuracies (e.g., `/api/chat` vs. `/api/generate`, `psutil` vs. `sysctl`/`platform`).
- Decisions about which features to defer (voice pipeline, Keychain, Android integration).

## Why This Disclosure Matters

Using AI to generate production-quality code and documentation is legitimate and increasingly common. However, it creates risks when:

1. **AI-generated claims are taken as ground truth.** This project performed explicit verification passes (Stages 7.1–7.6) to catch and correct inaccurate documentation.
2. **Status is inflated.** This project uses explicit status labels (Implemented / Partial / Planned / Deferred) and does not claim functionality that is not verified in source code.
3. **Authorship is obscured.** This document exists to prevent that.
